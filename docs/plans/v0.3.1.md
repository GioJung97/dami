# LocalFlow v0.3.1 — Fixes before v0.4

**Status: in progress on branch `v0.3.1`. M1 and M2 done (2026-11-06).**

**Goal:** fix four problems the 2026-11-05 review found. Each one loses speech or breaks trust, so per `CLAUDE.md` they come
before v0.4. Also bring README up to date with v0.3. Nothing else.

**Principle:** small and safe. Taking out less is better than changing meaning. If a fix grows past what's described here, stop
and ask. Things found along the way go in `docs/known-issues.md` or §6 below, not into this version.

Background: `docs/sessions/2026-11-05-v0.3-review.md`.

### M1 — A stray key doesn't discard a recording

**Today:** with a modifier-only shortcut (Right ⌘ + Right ⌥), any key pressed while it's held is taken as an app shortcut.
`HotkeyMachine` sends `.cancel`, and `DictationController.cancelRecording` throws the recording away with no message. A long
recording ends silently.

**Change:**
- `HotkeyMachine` remembers when the press started. A key down within `appShortcutWindow` (1.0 s) of it still cancels, as today.
  A key down after that does nothing to the recording: `isHeld` stays true, so letting go of the shortcut still ends it normally.
- This has to live in `HotkeyMachine`. If the cancel were only ignored in the controller, the machine would already consider the
  shortcut released, the real release would never arrive, and a hold-to-talk recording would run until the time limit.
- Give events a time. The tap can pass the event's timestamp, or the machine takes a clock. Tests inject times.
- The key isn't swallowed, as now, so the app gets it (with ⌘⌥ held). Not changing that.
- Key shortcuts (⌃ Space) and hands-free aren't affected. Check that with tests.

**Tests:** key within 1 s cancels; key after 1 s doesn't, and the release still arrives; a synthetic ⌘V still never cancels; key
repeat; a key after the window, then another press of the shortcut.

**Owner test:**
1. Hold the shortcut, say "오늘 회의는 세 시에 시작해요", tap Space halfway, keep talking, let go. The whole sentence should be pasted.
2. Hold the shortcut and press another key right away, as if using an app shortcut. Nothing should be pasted.

### M2 — Korean Replacements only change whole words

**Today:** a rule whose `find` isn't Latin matches anywhere (`ReplacementEngine.regex(for:)`). Fixing "세 시에" to "네 시에" suggests
"세 → 네". Accepting it turns "확인하세요" into "확인하네요" and "세상에" into "네상에" in every later dictation. Reproduced on
2026-11-05 by compiling the real `FixSuggestion` and `ReplacementEngine`.

**Change:**
1. **Matching, Hangul rules only:** a match needs no Hangul right before it, and right after it the end of the word or up to two
   known particles in a row, so "클라우드에서도" matches (owner, 2026-11-05). Move the particle list out of `FixSuggestion` so both use the same one.
   - Japanese and Chinese rules keep matching exactly, since those languages don't put spaces between words. Thai too.
   - **Added (owner, 2026-11-06): every spaced language matches whole words.** Only plain a–z rules matched whole words. A rule with
     an accent (Spanish "más", German "Müller", Vietnamese) or in Devanagari matched inside other words, case-sensitively: "más" →
     "mas" also changed "demás". Same kind of meaning change, and a few lines. Now any rule outside Hangul and the unspaced scripts
     matches whole words, ignoring case. A word ends at Hangul too, so "cloud code로" still matches a rule for "cloud code".
2. **Suggestions:** `FixSuggestion` doesn't suggest a Korean `find` of one syllable. A fix typed by hand in Dictionary is still
   allowed, since that's on purpose.
3. **Preview** uses the same matching (`matchedWords`), so the count it shows is the count that would change.
4. **Copy:** `DictionaryView.swift:139` says "Korean matches exactly". Change it to how matching works now.

**Existing rules:** the owner's 3 rules have never fired (`uses` 0), so the narrower matching changes nothing seen so far. Say this
in the milestone report.

**Tests:** "세 → 네" isn't suggested; a hand-made rule "세 → 네" leaves "확인하세요" and "세상에" alone, and changes "세 시에"; "클라우드 코드로" →
"Claude Code로"; "로컬플로우를" → "LocalFlow를"; a rule at the end of a sentence followed by punctuation; two particles ("클라우드에서도"); Latin rules unchanged; accented and Devanagari rules match whole
words; an English rule before a Korean particle; Japanese and Thai rules still match inside text. Add the "확인하세요" sentence to `bench/cleanup_cases.tsv` as `must_keep` with the rule
in place, if the eval can carry a rule. Otherwise keep it as a unit test.

**Owner test:**
1. In History, fix a dictation by changing one Korean syllable. No suggestion should appear.
2. Add a Replacement by hand, "세" → "네". Dictate "확인하세요" and "세 시에 봐요". Only the second should change. Then delete
   the rule.

### M3 — Deleting history really deletes it

**Today:** `deleteAllHistory()` deletes rows and the Audio folder. `LocalFlow.backup.sqlite`, the copy taken before the last
migration, stays, with 225 dictations on the owner's Mac. Deleted rows also stay in SQLite's free pages until they're overwritten,
since `secure_delete` is off.

**Change:**
- Turn `secure_delete` on for every connection, through GRDB's `Configuration.prepareDatabase`. Deleting one dictation, retention and
  "Don't keep" all benefit.
- `deleteAllHistory()` also deletes the backup file and runs `VACUUM` after the delete.
- The confirmation text says what goes: history, audio, fixes, and the backup copy. The Dictionary stays.
- **Backup kept 7 days (owner, 2026-11-05):** after a migration that went fine, the daily prune deletes the backup 7 days later.
  Otherwise individually deleted dictations live on in it until the next migration.

**Tests (scratch `Store` directory only):** write synthetic dictations with a unique marker string, delete all, then search the raw
bytes of the database file for the marker: it must not be there, and the backup file must be gone. The same marker check after
deleting one dictation.

**Owner test:** none needed beyond normal use. Optional: Delete all history on a test install, not the real one.

### M4 — Dropped dictations: counted by day, can be retried

**Today:** `dropCounts` has no date, so it can't tell before and after a fix. An empty result is counted as `hallucination`. A
dropped dictation shows "No speech recognized" and its audio is gone. On the owner's Mac: 26 hallucination drops, 10 of them 3 s
or longer. Whether they were real speech is unknown.

**Change:**
1. **Counters:** a date in the key, as `healthCounts` does, and a new reason `empty` apart from `hallucination` (a stock phrase).
   `scripts/health-check.sh` prints them by day. Keep the old undated counts as they are and stop adding to them.
2. **Retry:** a dropped dictation of 1 s or more, except one found silent, goes into the same in-memory list as failed dictations
   (at most 3, never on disk). The HUD shows "No speech recognized" with **Retry**, and the menu lists it like a failed one.
   **A drop for a stock phrase** (`hallucination`, such as "Thank you.") is different: the person may really have said it, and a
   rerun would likely give the same phrase. The HUD shows the filtered text with **Paste anyway** only, no Retry (owner,
   2026-11-05). The text stays in memory only, like the audio.
3. **Retry another way (owner, 2026-11-05).** The app already reruns an empty result without the prompt and with padding, so that
   isn't "another way". Whisper's own detection picks from 99 languages and heard Korean as Japanese before, so it isn't either.
   A retry from a drop runs with the **other** of the two languages forced: English if the drop was taken as the second language,
   and the other way round. Without the prompt and with the padding, as before. With no second language set, it runs English
   without the prompt. If it's still empty, say "Still no speech recognized" and drop it.
4. Count retries and whether they produced text, by day, numbers only. That tells whether this retry is worth keeping.

**Tests:** `DropStats` keys with a date; empty vs hallucination; a retry job carries the different options; the list stays at 3.

**Owner test:**
1. Hold the shortcut and say "네", the shortest thing you'd really say. If it says "No speech recognized", press Retry.
2. If you can: hold the shortcut and say "Thank you." If it's filtered, the HUD should offer Paste anyway, and pressing it pastes it.
3. Run `scripts/health-check.sh` and check that today's counts show up.

## 6. Noted for later

From the same review, not in this version. Pick these up when planning v0.4 or v1.0.

- **Latency on short clips:** about 1.3 s even under 5 s of audio, nearly all fixed cost. Record stage times as numbers first. The
  idea that the encoder runs twice (detection, then transcription) is still unverified. The largest user-facing speed gain is likely
  here, and v0.4 needs the time budget anyway.
- **Automatic capture on huge fields:** Terminal hands over its whole buffer, which is read and compared on the main thread once a
  second. Measure on a long document, and stop watching above a size if needed.
- **Migration check as a script:** done by hand with a scratch program in v0.2 and twice in v0.3. v0.4 likely needs one again.
- **Bluetooth:** about 3 of 8 wireless starts gave a saved dictation (v0.2 M2). Other people use AirPods more than the owner does,
  so find the cause before the v1.0 tester round.
- **"Coming later" screens:** Home card, Sync tab, Smart mode note. Part of v1.0 condition 1.
