# LocalFlow v0.4 — Implementation plan

**Status: in progress on branch `v0.4`. M1 and M2 done (2026-11-06). M3 done (2026-11-06): Qwen3-1.7B failed the pass line, and the owner
decided not to build M4. M5 done (2026-11-06).**

**Goal:** an optional Smart mode that cleans up text with a local LLM, without changing what the user meant. Light stays the default.
The owner decided on 2026-11-04 that the LLM is part of v1.0, so the question is how to add it safely, not whether. If no model passes
the check in M3, that result goes to the owner, and Smart isn't built into the app.

**Principle:** meaning damage matters more than anything Smart gains. Removing less is better than changing meaning. Small and
safe. If a milestone grows past what's described here, stop and ask. Things found along the way go in `docs/known-issues.md` or §7.

Background: the outline this replaces (2026-11-04), `docs/plans/v0.2.md` §7, `docs/sessions/2026-11-05-v0.3-review.md` §6.

## 2. Out of scope

Rewording, tone or style, summaries, translation, Command mode. Per-app styles and past corrections as examples (later). Whisper
changes, a lighter or heavier speech model. Streaming. Making Smart the default. Any API or network use beyond the one-time model
download.

## 3. Working rules

As in `CLAUDE.md`: a branch (`v0.4`), a milestone at a time, the owner tests in the real app before each commit, run
`scripts/health-check.sh` at the end of each milestone, never print or change the real database, ask before push or merge. Logs and
notes never hold dictated text: latency is numbers only.

## 4. The guardrail and the pass line (written before results)

### 4.1 Guardrail

The same rule in M3's script and in the app, in `LocalFlowCore` with tests.

- Align the output with the input by characters, ignoring spaces and punctuation. Only deletions are allowed: anything added fails.
- **Every deleted part must be one or more whole words of the input,** so "안했어" → "했어" fails: "안" is part of a word.
- Each deleted part needs a reason, or it fails:
  1. A filler candidate from a fixed list (Light's fillers plus context-dependent ones such as "like", "어", "그"). The model decides
     when one is a filler, the list only bounds what it may remove.
  2. A word repeated right after itself.
  3. A self-correction: a marker such as "아니", "아 아니", "no", "actually", "I mean", plus at most the 4 words right before it, and
     only when new words follow it.
- **Never deleted:** negations ("not", "n't", "never", "안", "못", "말", "없", "마" as words) and numbers. A number inside a
  self-correction's 4 words is the one exception ("3, no, 4" → "4").
- Spacing and punctuation may change freely.

This makes Smart fall back to Light more often and narrows what it can gain over Light: punctuation, Korean spacing, and fillers and
self-corrections that need context. That's chosen on purpose (owner, 2026-11-06).

### 4.2 Pass line

Run on `bench/cleanup_cases.tsv` after M2, with the model, prompt and settings fixed beforehand. The same run is repeated 3 times,
since sampling can vary even at temperature 0 across versions.

1. **Meaning changes: 0, in every run.** A meaning change is any word added that wasn't said, any content word removed that isn't a
   filler or a corrected-away part, a negation lost or added, a number, name, date or amount changed, or a translation. The guardrail
   (M3) rejects most of these mechanically. Whatever passes it is compared with `expected_smart`, and every case that differs is shown
   to the owner, who decides whether meaning changed. One is enough to fail.
2. **`must_keep` cases: words unchanged.** After normalizing punctuation and spacing, the output's words equal the input's.
3. **Better than Light on the Smart-target cases** (`must_fix` and the new M2 cases, about 45–50): matching `expected_smart` exactly,
   spacing and punctuation included, **at least 10 more cases than Light, and at most 2 cases that Light gets right and Smart
   doesn't.**
4. **Time:** within the budget in §1 on M1's short clips, measured the same way as M1, model loaded. First use after idle is
   reported apart.
5. **Memory:** Whisper and the model loaded together stay under 4 GB of the app's footprint on this Mac, measured as Activity Monitor
   does (the whole footprint, Metal included), and unloading the model brings it back to where it was.

If 1 or 2 fails, Smart doesn't go into the app. If only 3, 4 or 5 fails, report to the owner with the numbers before deciding.

**What a pass can't tell:** 0 meaning changes in about 100 cases only says the real rate is likely under about 3% (the rule of three:
3 / n). Rarer damage can't be seen in a set this size. README says so, and Smart stays optional.

### M1 — Where the time goes today

**Why:** dictations under 5 s take about 1.3 s, nearly all fixed cost (`docs/sessions/2026-11-05-v0.3-review.md`). Smart adds time on
top, so the budget needs to know what's there. The idea that the encoder runs twice, once to detect the language and once to
transcribe, is still unverified.

**Change:**
- **First, Paste anyway** goes through the processing order and waits while a recording is on, instead of pasting at once
  (v0.3.1 review).
- Time each stage of a dictation: language detection, transcription (with any retry), cleanup, paste up to sending ⌘V (the 0.3 s
  clipboard restore after it isn't waiting time). Log the numbers only, under the `latency` category, with the audio length,
  language and whether it's the first dictation after a while idle. Keep it, since M4 needs the same numbers for Smart.
- After the owner has dictated for a day, read the log and report: median and slowest per stage, for short (under 5 s) and longer
  dictations, Auto against a fixed language.
- If detection really runs the encoder a second time, say how much it costs. Fixing it isn't part of this milestone: report and ask.

**Owner test:** dictate as usual for a day, including some short phrases in Auto. M2's case review runs in the same days.

**Done when:** the stage times are in the session notes and the owner has seen them.

### M2 — Expected answers and more cases

**Why:** the 82 cases were written for the rules. Few test what Smart is for: Korean spacing (never measured, since `bench/score.py`
ignores spaces), punctuation, self-corrections in Korean and mixed sentences.

**Change:**
1. Draft `expected_smart` for all 82 cases. For `must_keep`, the input with only punctuation and spacing allowed to change.
2. Add about 20 cases in Smart's scope, with the owner: Korean spacing, run-on sentences without punctuation, self-corrections in
   Korean and mixed sentences, and traps where a correction-like phrase isn't one ("아니 그게 아니라" as real speech). Also cases
   that are risky for an LLM: questions and instructions it might answer or carry out ("이거 영어로 번역해줘", "summarize this"),
   negations, a sentence over 60 words, and code names. Each with
   `expected_light` as Light gives it today, so the rules' score doesn't move.
3. The owner reviews every `expected_smart` and every new case. Nothing is run against a model before that.
4. `localflow-eval` reports `expected_smart` for Light too, as the number Smart has to beat.

**Decided while drafting (owner, 2026-11-06, as recommended):**
- Verbal-habit phrases ("So basically what I'm trying to say is that", "그러니까 제 말은") stay. Removing them is closer to
  rewording, and the guardrail has no reason to allow it.
- Smart runs only on English, Korean and mixed dictations. Other languages get Light, since words like "um" are real there and
  nothing else has been tested.
- In `must_keep`, punctuation, spacing and the first letter's case may change. Words may not.
- `expected_smart` may list several right answers, separated by ` || `. Matching any one counts.

**Owner test:** review the cases. Given as a short list in Korean chat, ten at a time, not as a file.

**Done when:** every case has a reviewed `expected_smart`, and the pass line in §4 is unchanged or changed by the owner before M3.

### M3 — The model, outside the app

**Change:**
- A Python script in `bench/` runs a candidate with `mlx-lm` on the cases, thinking off, temperature 0, three runs.
- Start with Qwen3-1.7B 4-bit. Try one smaller and one larger only if the first fails on quality or time, not to shop around.
- **Guardrail** from §4.1, the Swift rule in `LocalFlowCore` called from the script (or a byte-for-byte port with shared test cases),
  so M3 and M4 judge alike. A result that fails it counts as Light's output, and the count is reported by reason.
- **Check early that MLX Swift builds** in this project (Swift 5.10, xcodegen), with a throwaway target. If it doesn't, stop and ask
  before M4 is planned around it.
- Replacements run before the model, as today, and again after it.
- Report against §4: meaning changes with every differing case shown, `must_keep`, `must_fix` against Light, time per case, memory.

**Owner test:** read the differing cases and judge meaning. Nothing in the app changes.

**Done when:** the owner has the report and has decided: build M4, or not.

### M4 — Smart mode in the app, if M3 passed

**Change:**
- **Model download** only when Smart is turned on, with its size and progress, and checked complete like the speech model. Never
  otherwise. Turning Smart off asks every time: keep the model (about 1 GB) or delete it.
- **Runs with MLX Swift**, the same model and prompt as M3, thinking off.
- **Guardrail and fallback:** M3's guardrail on every result. If it fails, or the model takes longer than a limit proportional to the
  text length, or it isn't loaded yet, Light's text is pasted. The fallback is counted by reason, numbers only. Speech is never lost to
  Smart.
- **Preload** about 300 ms into a hold, and unload after a while idle. Check that unloading frees memory.
- **8 GB Macs:** Smart is off by default and marked untested.
- **History:** Light's text in `rulesText`, Smart's in `finalText`. New columns: Smart used or not, why it fell back, the model
  name, the model's time. Schema change, checked on a copy first.
- **Learning:** for a Smart dictation, a fix gives a suggestion only if the word being fixed is in Whisper's own text (`rawText`), so
  the model's mistakes don't become Replacements.
- **Same eval through Swift:** run every case through the app's Smart code and recheck §4. Python and Swift can differ in tokenizer,
  chat template and generation settings.
- **Settings:** Smart in the cleanup mode picker, with a one-line description of what it does and doesn't do.

**Tests:** guardrail cases in `LocalFlowCore`: an added word, a lost negation ("보내지 마" → "보내지", "안했어" → "했어"), a deleted
number outside a self-correction, a translated sentence, a deleted non-filler word all fall back to Light; a filler, a repeat and
"3, no, 4" pass. Timeout falls back; fallback counted.

**Owner test:**
1. Turn Smart on and let the model download.
2. Read these, one dictation each: "음 그러니까 내일, 아 아니 모레 회의 잡아줘", "I think we should, uh, push it to Friday",
   "생각해봐야 될 것 같아요 그리고 내일 다시 얘기해요", "Don't send it yet".
3. Check that each kept what you meant, and that nothing felt slower than about half a second extra.
4. Turn Smart off and dictate once: Light as before.

**Done when:** the owner test passes, fallbacks are counted, and memory is back down after unloading.
